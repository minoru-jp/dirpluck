# Archive planning

## SPEC_095

For a Target resolved through a Scope, the source root is the one-segment Target entry name: the directory name for a directory Target or the file name for a file Target. The logical Scope name is not implicitly included in the archive path.

level: MUST

related: [SPEC_050](runtime-targets.md#spec_050)

## SPEC_096

When a source has an effective Layout, its final Archive root uses the declared Layout name as the top-level component, followed by the Target source root or effective Always name. Without Layout, a Target keeps the existing optional Scope-Namespace prefix behavior, while an Always source uses its effective Always name as the final Archive root. Effective Layout and Namespace are not combined on the same source. Directory sources place selected paths relative to the source directory below the final Archive root; a file Target uses the final Archive root itself as its single file entry. Declaring a Layout alone does not create an Archive directory entry.

level: MUST

## SPEC_097

The Archive root for an Always source or an activated Extra source is derived from its TOML source identifier, not from the filesystem source location. Without Layout, that identifier is the source root; with Layout, it appears below the Layout directory.

level: MUST

related: [SPEC_063](namespace.md#spec_063)

## SPEC_098

Every resolved source final Archive root must be unique under a case-insensitive comparison regardless of source role. A Target and an Always or activated Extra source that resolve to the exact same spelling are an error rather than a shared destination region. Roots such as `App` and `app` that differ only in case are also ambiguous and invalid. Because Layout is part of the final Archive root, the same uniqueness rule applies after Layout placement. The spelling actually written to the Archive is preserved.

level: MUST

related: [SPEC_168](namespace.md#spec_168)

## SPEC_099

If different physical files collide at the same archive path, planning fails with an ambiguity error. If the same physical file maps to the same archive path more than once, it is written once. If the same physical file is selected through different resolved sources and maps to different archive paths, each archive path is written. Because a file Target uses its final Archive root as the file entry itself, planning also rejects a file/directory path conflict where that file path is an ancestor or descendant of another archive file path.

level: MUST

## SPEC_100

Each source is selected independently within its own source boundary. Overlap between source selections does not merge their Selection semantics; it matters only when final Archive entries or generated README source information would collide.

level: MUST

## SPEC_101

The root-level `README.md` path is reserved for the Archive index generated by `dirpluck`. If the first component of a resolved source's final Archive root matches `README.md` case-insensitively, planning fails instead of placing a source at or below that reserved path. This applies regardless of whether Layout, Namespace, or the source root itself provides that first component.

level: MUST

## SPEC_102

The generated root `README.md` is an index of Archive contents, not a resolution report. If effective `[about].description` exists, it is included as the overall Archive description regardless of the resolved source mix. In addition, exactly one conditional description is included when configured: `description_no_targets` for Always-role-only sources, `description_no_always` for Target-only sources, or `description_empty` when neither role resolves. No conditional description is added when both roles are present. An activated Extra has the same fixed / Always role as an Always source for this decision. Source presence is determined by the resolved source role rather than selected-file count, so a source with `allow_empty = true` and zero selected files still counts as present. Exact Markdown headings, punctuation, whitespace, and other presentation details are not a stable machine-readable compatibility interface.

level: MUST

## SPEC_103

For each actually used Layout that has a `description`, the generated README includes identifiable information for that Layout directory and description exactly once. A Layout without a description remains valid for placement and does not require a Layout-description entry. Source listings represent Always sources and activated Extra sources before Targets and place each source or group description before auxiliary metadata such as file counts, source paths, or overlap information. Targets are grouped by Scope and show the Scope identity and `scope.description` as group context. Directory Targets are represented by final Archive root under that Scope's Pluck group, and Scope / Pluck Selection descriptions are not repeated for every Target in the same Scope. File Targets do not use Pluck and are represented directly under the Scope group as atomic sources. Always sources and activated Extra sources show their final Archive root and their own Selection `description`. Multi-line descriptions are preserved. Exact heading levels, inline-code spelling, labels, and whitespace are presentation details rather than a stable machine-readable interface.

level: MUST

## SPEC_104

When Archive planning needs to report overlap or collision-relevant source information, the generated README / preview representation must preserve the meaning needed by a human reader. Exact labels, placement, and formatting are not a stable machine-readable compatibility interface.

level: MUST

## SPEC_106

The generated README may record Scope identity and directory-Target Pluck context for Target grouping. The README itself explains that a Scope identity represents only the selection range used to find Targets and does not imply priority, importance, or hierarchy between them; any additional meaning comes from `scope.description`. The selected Pluck Case name, Configuration path or table, base chain, and similar execution provenance are not recorded by default. Physical overlap is identified by final Archive root rather than by Target reference. Source filesystem paths are also omitted by default. When source-path presentation is requested for a normal build, each relevant source section includes the resolved source filesystem path using `/` separators. Directory sources use the directory path and file Targets use the file path. This option does not change Archive paths or Selection semantics. Exact labels and placement are presentation details and are not a stable machine-readable interface.

level: MUST
